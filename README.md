# OmniTech — інтернет-магазин техніки

[![Docker](https://github.com/Hyrysake/omnitech/actions/workflows/docker.yml/badge.svg)](https://github.com/Hyrysake/omnitech/actions/workflows/docker.yml)
[![Тести](https://github.com/Hyrysake/omnitech/actions/workflows/tests.yml/badge.svg)](https://github.com/Hyrysake/omnitech/actions/workflows/tests.yml)

Навчальний командний проєкт з дисципліни «Основи програмної інженерії».
OmniTech складається з двох частин в одному репозиторії:
- **`backend/`** — REST API на FastAPI (лабораторна 05);
- **`frontend/`** — сайт на Vite + JavaScript (лабораторна 06). Кожна сторінка отримує й надсилає дані лише через це API.
Версії сайту на Flask з лабораторних 03 і 04 збережено в історії Git, позначки `lab03` і `lab04`.

Бекенд перевіряють автоматичні тести pytest (лабораторна 07): опис і результати — у [TESTING.md](TESTING.md).

Увесь проєкт запускається в контейнерах Docker (лабораторна 08): розділ «Запуск у Docker» нижче, докладна документація — у [docs/docker/](docs/docker/index.md).

## Технології

| Що | Чим | Навіщо |
|---|---|---|
| Вебфреймворк | FastAPI | маршрути, перевірка даних, автоматична документація `/docs` |
| Сервер | Uvicorn | запускає застосунок FastAPI (ASGI-сервер) |
| Перевірка даних | Pydantic v2 | схеми запитів і відповідей, усі помилки полів разом (422) |
| База даних | SQLite + SQLAlchemy 2.0 (ORM) | таблиці як класи Python; перейти на PostgreSQL — змінити одну адресу |
| Налаштування | pydantic-settings, файл `.env` | секретний ключ і адреси не пишуться в коді |
| Вхід | OAuth2 + JWT (PyJWT), паролі argon2 (pwdlib) | вхід без сесій на сервері: токен у заголовку `Authorization` |
| Картинки | python-multipart, Pillow | завантаження файлів і перевірка, що це справді картинка |
| Тестування API | Postman | колекція `backend/postman/postman_collection.json` |
| Автоматичні тести | pytest, pytest-cov, `TestClient` (httpx2) | unit і integration тести бекенду, покриття коду ([TESTING.md](TESTING.md)) |
| Контейнери | Docker, Docker Compose (`include`, профілі, томи) | один запуск `docker compose up` на будь-якому комп'ютері; база SQLite у volume |
| Reverse proxy | Nginx (образ `nginx:alpine`) | віддає зібраний сайт і пересилає `/api` та `/media` на бекенд, тож сайт і API на одній адресі |
| Безперервна перевірка | GitHub Actions | тести запускаються самі після кожного push і в кожному Pull Request |
| Клієнтська частина | Vite 8 + JavaScript (ES-модулі), без фреймворків | сервер розробки з миттєвим оновленням, збирання сторінок у `dist/` |
| Оформлення | Tailwind CSS 4 (npm, плагін `@tailwindcss/vite`) | дизайн-система з лабораторних 03–04: кольори, кнопки, картки, темна тема |
| Шрифти й іконки | Fontsource (Montserrat, Cormorant), Phosphor Icons — з npm | сайт однаково виглядає і без доступу до сторонніх серверів |
| Анімація прокрутки | GSAP 3.15.1 з плагіном ScrollTrigger (ліцензія GSAP «no charge», безкоштовна, але **не MIT**) | закріплена розповідь на головній (`src/layout/scroll-fx.js`) і спільний таймер з Lenis; завантажується окремим файлом лише на публічних сторінках |
| Плавна прокрутка | Lenis 1.3.27 (ліцензія MIT) | м'яка прокрутка коліщатком (lerp 0.1); вимикається перемикачем «Рух», системним «Зменшити рух» і в полях форм |
| Живе тло | власний WebGL2-шейдер (`src/layout/gl-contours.js`) з чужим кодом шуму simplex: `webgl-noise`, Ashima Arts і Stefan Gustavson (ліцензія MIT) | золоті контурні лінії на тлі; без WebGL2 — SVG-плитка `public/contours.svg` |

Повний список сторонніх бібліотек і ліцензій: [THIRD-PARTY.md](THIRD-PARTY.md).

## Як запустити

Потрібні два термінали VS Code: в одному працює API (`backend`), у другому — сайт (`frontend`).

### API (backend)

Потрібен Python 3.11 або новіший. Усі команди — у терміналі VS Code, з папки `backend`:

```powershell
cd backend
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

Файл налаштувань `backend/.env` із власним секретним ключем (у Git не потрапляє; зразок усіх налаштувань — `.env.example`):

```powershell
python -c "import secrets; open('.env', 'w').write('SECRET_KEY=' + secrets.token_urlsafe(32) + chr(10))"
```

Демо-дані й запуск:

```powershell
python -m app.seed --reset
uvicorn app.main:app --reload
```

- API: <http://127.0.0.1:8000/api/v1/products>
- Документація (Swagger UI): <http://127.0.0.1:8000/docs>, альтернативний вигляд: <http://127.0.0.1:8000/redoc>

**Демо-акаунти** (створює `python -m app.seed`):

| Роль | Пошта | Пароль |
|---|---|---|
| Адміністратор | `admin@omnitech.example` | `admin123` |
| Клієнт | `client@omnitech.example` | `client123` |

**Як увійти в `/docs`:** кнопка **Authorize** → пошта в полі `username`, пароль у полі `password` → **Authorize**. Після цього кожен запит із `/docs` надсилає токен сам.

### Сайт (frontend)

Потрібен Node.js 20.19+ або 22.12+ (перевірити: `node -v`). У другому терміналі:

```powershell
cd frontend
npm ci
npm run dev
```

- `npm ci` встановлює пакети точно тих версій, що записані в `package-lock.json` (у Git папка `node_modules` не потрапляє).
- Сайт: <http://localhost:5173>. API при цьому має працювати в першому терміналі.
- Адреса API за замовчуванням — `http://127.0.0.1:8000`. Іншу можна вказати у файлі `frontend/.env` (зразок — `.env.example`).
- Готовий сайт для розміщення на сервері: `npm run build` (папка `frontend/dist`), перегляд зібраного: `npm run preview`.

### Тести (backend)

У терміналі бекенду, з активованим `.venv` (сервер для тестів запускати не треба, файл `.env` теж не потрібен):

```powershell
cd backend
pip install -r requirements-dev.txt
pytest
```

- `pytest -v` — назва й результат кожного тесту; `pytest tests/unit` — лише швидкі unit тести.
- `pytest --cov=app --cov-report=term-missing` — покриття коду тестами.
- Тести працюють з тимчасовою базою: робоча `backend/data/omnitech.db` не змінюється.
- Докладно: [TESTING.md](TESTING.md).


## Запуск у Docker (лабораторна 08)

Увесь проєкт запускається в контейнерах: Nginx віддає сайт і пересилає запити `/api` на бекенд, бекенд зберігає SQLite у volume.
Потрібні Docker Desktop (на Windows з WSL2) і Git. Python і Node.js на комп'ютері для цього не потрібні.

```bash
git clone https://github.com/Hyrysake/omnitech.git
cd omnitech
cp .env.example .env            # PowerShell: Copy-Item .env.example .env
docker compose up --build
```

Сайт: <http://localhost:8080>, документація API: <http://localhost:8080/docs>. Демо-акаунти ті самі, що й вище.
Зупинити: `docker compose down` (база лишається у volume), стерти й базу: `docker compose down -v`.
Фоновий запуск з очікуванням готовності: `docker compose up --build --wait -d`, стан: `docker compose ps`.

| Режим | Команда |
|---|---|
| Робочий (prod) | `docker compose up --build -d` |
| Розробка (код з вашої папки, автоперезапуск, сайт на `:5173`) | `docker compose -f compose.dev.yaml up --build` |
| Копія бази | `docker compose --profile ops run --rm backup python /scripts/backup_db.py` |
| Повна перевірка | `python scripts/docker_smoke.py` |

### Образи, сервіси й томи

| Сервіс | Образ | Деталі |
|---|---|---|
| `backend` | `python:3.13-slim`, багатоетапна збірка, ~248 МБ | FastAPI + Uvicorn (один процес), користувач uid 10001, `HEALTHCHECK` на `/api/health`, `restart: unless-stopped` |
| `frontend` | `node:22-alpine` (збирання) → `nginx:alpine`, ~99 МБ | зібраний сайт, reverse proxy на `backend`, 404 для невідомих адрес |
| `backup` | `python:3.13-slim` + скрипти | профіль `ops`: копії й відновлення SQLite через `Connection.backup()` |

| Volume | Папка в контейнері | Що там |
|---|---|---|
| `omnitech-data` | `/app/data` | `omnitech.db` і файли WAL; монтується на ПАПКУ, власник uid 10001 задано в образі |
| `omnitech-media` | `/app/media` | завантажені картинки товарів |
| `omnitech-backups` | `/app/backups` | резервні копії бази |

Змінні (`HTTP_PORT`, `SECRET_KEY`, `APP_ENV`, `LOG_LEVEL`, `SEED_ON_START`) задаються у `.env`; зразок — `.env.example`, опис — у [docs/docker/config.md](docs/docker/config.md).

### Чому так

- **Багатоетапна збірка й `slim`**: бібліотеки ставляться в окремому етапі, у фінальний образ іде лише готове середовище без кешу pip. Alpine не використано, бо pillow і argon2 під musl збираються гірше.
- **Кешування шарів**: `requirements.txt` копіюється раніше за код, тому після зміни коду бібліотеки не ставляться заново.
- **SQLite у named volume на папці**: файли `-wal` і `-shm` потребують папки, у яку можна писати; bind mount на Windows ненадійний для блокувань SQLite.
- **Один процес Uvicorn**: SQLite підтримує одного писача за раз.
- **Копії через `backup()`**, а не копіюванням файлу: цілісно навіть під час запису в режимі WAL.
- **Nginx**: сайт і API на одній адресі, тому CORS не потрібен; `VITE_API_URL` під час збирання порожня.

Докладно: [архітектура](docs/docker/architecture.md), [конфігурація](docs/docker/config.md), [тестування](docs/docker/testing.md), [резервні копії](docs/docker/backup.md), [типові проблеми](docs/docker/troubleshooting.md) (там і що робити, якщо Docker не запускається на вашому комп'ютері).

## Структура бекенду

```text
backend/
├── app/
│   ├── main.py            застосунок: CORS, обробники помилок, підключення маршрутів, /media
│   ├── api/
│   │   ├── router.py      усі адреси API в одному місці (/api/v1, /api/v2)
│   │   └── deps.py        залежності: сесія бази, поточний користувач, адмін, сторінки
│   ├── core/              налаштування, безпека (хеші, JWT), помилки, спільні перевірки
│   ├── db/                підключення до бази, базовий клас моделей, пагінація
│   ├── models/            таблиці бази (класи SQLAlchemy)
│   ├── schemas/           що API приймає і віддає (класи Pydantic)
│   ├── services/          логіка: що саме робити з даними (без HTTP)
│   ├── routers/           ендпоінти: v1/ і v2/
│   └── seed/              демонстраційні дані (python -m app.seed)
├── tests/
│   ├── conftest.py        спільні fixtures: тимчасова база, тестовий клієнт, користувачі, товари
│   ├── unit/              тести окремих функцій, без бази
│   └── integration/       тести ендпоінтів API з тестовою базою
├── pytest.ini             налаштування pytest
├── .coveragerc            налаштування вимірювання покриття
├── requirements-dev.txt   бібліотеки для тестів (pytest, pytest-cov, httpx2)
├── postman/               колекція Postman і картинка для тесту завантаження
├── data/                  файл бази omnitech.db (у Git не потрапляє)
├── media/                 завантажені картинки (у Git не потрапляють)
├── requirements.txt
└── .env.example           зразок налаштувань; справжній .env у Git не потрапляє
```

Запит проходить шари по черзі: **router** (адреса, коди відповіді) → **schema** (перевірка даних) → **service** (логіка) → **model** (база). Кожен шар знає лише про сусідній, тому код легко читати й перевіряти частинами.

## Структура фронтенду

```text
frontend/
├── index.html, catalog.html, …   сторінки сайту: розмітка й порожні блоки для даних
├── admin/                       сторінки адмін-панелі
├── public/                      файли без обробки: значок сайту, картинка-заглушка, contours.svg (запасне тло)
├── src/
│   ├── api/                     client.js — єдина функція запитів apiRequest(); config.js — адреса API
│   ├── auth/                    токен у localStorage, перехід на вхід і повернення назад
│   ├── store/                   кошик у localStorage, список бажань (дані на сервері)
│   ├── boot.inline.js           єдиний вхідний скрипт усіх сторінок (тема, рух, режим сторінки, заставка)
│   ├── layout/                  шапка з меню на весь екран, підвал, ефекти (заставка, WebGL-тло, змійки, поява слів, шторка між сторінками, плавна прокрутка), спільний старт сторінки
│   ├── ui/                      будова елементів, повідомлення, стани списків, форми, картки
│   ├── pages/                   код кожної сторінки (pages/admin — адмін-панелі)
│   └── styles/                  main.css (Tailwind, токени), site.css (оболонка й ефекти), pages.css (окремі сторінки), icons.css
├── vite.config.js               список сторінок для збирання, порт 5173
├── package.json, package-lock.json
└── .env.example                 зразок адреси API
```

У кожній HTML-сторінці замість довгого скрипта в `<head>` стоїть лише маркер `<!--boot-->`: Vite підставляє на його місце вміст `src/boot.inline.js` (плагін у `vite.config.js`), тож правити його треба в одному місці. Кожна сторінка — це HTML-файл і однойменний модуль у `src/pages`. HTML містить сталу розмітку (заголовки, форми), а модуль завантажує дані з API й будує з них списки та картки.

## Ефекти і рух

Усі ефекти лежать у `src/layout/` і `src/styles/site.css`. Вони лише прикраса: без них сайт працює так само.

- **Режими сторінок.** Скрипт `src/boot.inline.js` ставить на `<html>` атрибут `data-mode`. `full` (публічні сторінки): усі ефекти. `calm` (кошик, оформлення, вхід, реєстрація, профіль, замовлення, список бажань): тло, поява тексту й шторка між сторінками. `admin`: без ефектів.
- **Перемикач «Рух».** Кнопка в підвалі й меню, вибір у `localStorage` (ключ `motion`). Системне налаштування `prefers-reduced-motion` за замовчуванням вимикає рух. Без руху: немає заставки, плавної прокрутки, закріплення розповіді й шторки; лінії повністю намальовані, текст видно одразу, тло — один нерухомий кадр.
- **Тло.** Фрагментний WebGL2-шейдер малює повільні золоті контурні лінії (на курсор вони не реагують). Запасний варіант: SVG-плитка `public/contours.svg`; вона вмикається, коли немає WebGL2, відеокарта програмна, пристрій слабкий, увімкнена економія трафіку або сторінка спокійна.
- **Заставка** (лічильник 0 → 100, «+», діагональне вікно, близько 2,5 с): один раз за сесію (`sessionStorage`), лише при вході з головної.
- **Змійки** (`snake.js`): SVG-лінії малюються прокруткою через `stroke-dashoffset`; під текстом лінія зникає, щоб не псувати контраст.
- **Шторка між сторінками**: міждокументні View Transitions (Chrome, Edge); в інших браузерах звичайний перехід.
- **Закріплена розповідь, плавна прокрутка**: GSAP + ScrollTrigger і Lenis, окремий файл `scroll-fx.js`, лише на екрані від 768 px.
- **Курсор-крапка**: лише з мишею, від 1024 px, на публічних сторінках, коли рух увімкнено.
- **Каталог**: плаваючі фільтри (`ui/floating-filters.js`) і власний випадний список (`ui/select.js`, ARIA combobox у верхньому шарі браузера).

## Як сайт працює з API

- **Один шлях для всіх запитів.** Сторінки викликають `apiRequest()` з `src/api/client.js`, а не `fetch()` напряму. Там зібрано все спільне: адреса API, формат JSON, тайм-аут 10 секунд, перевірка `response.ok` і перетворення будь-якої невдачі на `ApiError` з українським текстом.
- **Помилки, які бачить користувач:**
  - сервер недоступний → «Не вдалося з'єднатися із сервером…» і кнопка «Спробувати ще»;
  - сервер не відповідає 10 секунд → «Сервер не відповідає…»;
  - 422 → повідомлення під кожним полем форми (сервер повертає список `errors`);
  - 404 → «Не знайдено» на місці вмісту; 409, 400, 5xx → текст `detail` від сервера.
- **Перевірка форм у браузері** повторює правила сервера (довжини, пошта, телефон, ціна), тож людина бачить помилку одразу. Сервер однаково перевіряє все сам.
- **Застарілі відповіді не показуються:** коли фільтр змінено ще до відповіді на попередній запит, той запит скасовується (`AbortController`).
- **Захист від XSS:** дані з API потрапляють на сторінку лише як текст (`src/ui/dom.js` будує елементи й додає рядки текстовими вузлами). У проєкті немає `innerHTML`, тож `<script>` у назві товару чи тексті відгуку так і лишається текстом.
- **CORS:** сайт (порт 5173) і API (порт 8000) — різні джерела (origin), тому API явно дозволяє запити саме з `http://localhost:5173` і `http://127.0.0.1:5173`. Браузер перед запитами з токеном чи JSON робить попередній запит `OPTIONS`; його видно у вкладці Network.
- **Вхід:** токен з відповіді `POST /auth/token` зберігається в `localStorage` разом із часом, коли він перестане діяти. Запити, яким потрібен вхід, додають заголовок `Authorization: Bearer …`. Якщо сервер відповів 401 (токен минув або акаунт видалено), сайт забуває токен і веде на сторінку входу, а після входу повертає туди, де людина була (`?next=`; приймаються лише адреси цього сайту).
- Перевірки «лише для покупця» й «лише для адміна» на сторінках — для зручності. Права перевіряє сервер: без потрібної ролі кожен запит отримає 401 чи 403.
- **Кошик** зберігається в `localStorage` лише як номери товарів і кількість. Ціни й суми щоразу рахує сервер (`POST /cart/preview`), тож підробити ціну в браузері неможливо.

## Вхід і права

- `POST /api/v1/auth/token` приймає форму (`username` = пошта, `password`) і повертає **JWT** — підписаний рядок з номером користувача й терміном дії (60 хв). Роль у токен не записується: сервер щоразу бере її з бази, тож зміна ролі діє одразу.
- Клієнт надсилає токен з кожним запитом: `Authorization: Bearer <токен>`. Сервер нічого не зберігає між запитами (stateless): він лише перевіряє підпис і термін.
- Немає токена або він недійсний → **401**. Токен правильний, але роль не та → **403**.
- Виходу на сервері немає: щоб вийти, клієнт просто видаляє токен.
- Паролі зберігаються лише як хеш argon2. Для неправильної пошти й неправильного пароля відповідь однакова.

## Помилки

Будь-яка помилка має той самий формат:

```json
{
  "detail": "Дані не пройшли перевірку.",
  "errors": [
    {"field": "price", "message": "Має бути більше за 0."},
    {"field": "name", "message": "Мінімальна довжина — 3 симв."}
  ]
}
```

`errors` є лише тоді, коли помилка стосується конкретних полів. Усі помилки полів повертаються разом, тож клієнт виправляє все за один раз.

| Код | Коли |
|---|---|
| 200 / 201 / 204 | успіх / створено (з `Location`) / успіх без тіла |
| 400 | дію виконати не можна (неправильний поточний пароль, мінімальна ціна більша за максимальну) |
| 401 | потрібно увійти |
| 403 | недостатньо прав |
| 404 | запису немає (або чуже замовлення) |
| 405 | метод не підтримується для адреси |
| 409 | конфлікт з даними: пошта зайнята, другий відгук, товар у замовленнях, категорія з товарами |
| 413 / 415 | файл завеликий / не картинка |
| 422 | дані не пройшли перевірку |
| 500 | помилка сервера (подробиці лише в журналі сервера) |

## Валідація

- **Типи й формат** перевіряє Pydantic за схемами в `app/schemas/`. Ціни, оцінки, кількості й номери приймаються лише справжніми цілими числами JSON: `"100"`, `12.5` і `true` не пройдуть.
- **Правила з форм сайту** (лабораторна 04): ім'я від 2 символів, пароль від 6, телефон 10–13 цифр, адреса доставки від 5, назва товару від 3, опис до 1000, відгук від 5 до 1000 символів, повідомлення від 10 до 2000.
- Пробіли на початку й у кінці рядків відрізаються. **Невідоме поле — помилка**, тож одруківку (`prise` замість `price`) видно одразу.
- **Перевірки в базі:** існування категорії, унікальність пошти й назви категорії, один відгук на товар. Обмеження `CHECK`, `UNIQUE` і зовнішні ключі є й у самій базі, як останній рубіж.
- **Картинки:** лише JPEG, PNG або WebP до 5 МБ. Тип визначається за вмістом файлу (Pillow), а не за назвою. Ім'я файлу генерує сервер.

## Версії API

`/api/v1` і `/api/v2` працюють одночасно. v2 змінює формат товару, тому це окрема версія, а не правка v1:

| | v1 | v2 |
|---|---|---|
| категорія | `"category_id": 1` | `"category": {"id": 1, "name": "Ноутбуки"}` |
| рейтинг | окремим запитом до відгуків | `"rating": {"average": 4.5, "count": 2}` у кожному товарі |

Клієнти, написані під v1, працюють без змін.

## Тестування в Postman

Колекція: `backend/postman/postman_collection.json` (102 запити в 11 папках).
- **Імпорт:** Postman → Import → файл колекції.
- **Запуск:** запустіть сервер на свіжій базі (`python -m app.seed --reset`), потім Run collection.

## Висновки (лабораторна 08)

- Увесь проєкт (сайт, API, база) запускається однією командою `docker compose up --build`. Сайт і API стоять за Nginx на одній адресі, тому CORS не потрібен.
- База SQLite лежить у named volume на папці `/app/data` і переживає `docker compose down`. Папка, а не файл, бо режим WAL створює поруч файли `-wal` і `-shm`. Процес працює не від root (uid 10001).
- Багатоетапна збірка на `python:3.13-slim` і порядок шарів (спершу `requirements.txt`, потім код) дали образ близько 248 МБ замість 295 і швидку перезбірку.
- Healthcheck, `depends_on: service_healthy` і `restart: unless-stopped` дозволяють запускати сервіси в потрібному порядку й піднімати бекенд після збою.
- Резервні копії робимо через `Connection.backup()`, а не копіюванням файлу, бо в режимі WAL файл не містить усіх даних. Перед відновленням поточна база зберігається.
- Кожен учасник змінював лише свої файли, а заглушки сервісів в основі дозволили перевіряти свою частину, не чекаючи чужих. Основа й три пакети зливаються в будь-якому порядку.

## Лабораторна 06: редизайн і розподіл роботи

### Дизайн, теми й доступність
- **Дві теми** — світла й темна. За замовчуванням береться тема системи, перемикач у шапці її змінює, вибір зберігається. Скрипт `boot.inline.js` у `<head>` ставить тему до першого малювання, тому сторінка не «блимає».
- **Той самий колір і шрифти**: тепле каміння й золото, Cormorant для заголовків, Montserrat для тексту.
- **Меню на весь екран** — елемент `<dialog>`: Esc закриває, фокус не виходить за межі меню, решта сторінки неактивна.
- **Ефекти** (докладніше в розділі «Ефекти і рух»): заставка з лічильником 0 → 100, золоті контурні лінії на тлі, права смужка прокручування, золоті лінії, що малюються прокруткою, поява тексту по словах, закріплена розповідь, золота шторка між сторінками, ілюстрації товарів із ліній. Ідеї взято з чотирьох сайтів (santalarch.com, landonorris.com, lusion.co, noomoagency.com), але без 3D-об'єктів, підпису від руки й тексту, що біжить. Усе вимикається перемикачем «Рух» і системним `prefers-reduced-motion`.
- **Швидкість**: жодних скриптів із чужих серверів, кожна сторінка вантажить лише свій код, GSAP і Lenis (близько 50 КБ у gzip) завантажуються окремим файлом після першого малювання. Вимог до швидкості в лабораторній немає, і ефекти її трохи знижують (див. результати тестування).
- **Доступність**: посилання «Перейти до вмісту», помітна рамка фокуса, підписи до кожного поля, `aria-live` для лічильників і помилок, контраст не нижчий за WCAG AA в обох темах, цілі натискання від 44 px; прикраси мають `aria-hidden`.
